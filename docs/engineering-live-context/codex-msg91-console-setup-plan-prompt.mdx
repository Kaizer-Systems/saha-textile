## 1. What "done" means

Transactional OTP delivery works end to end from the running API: an email code reaches a real
inbox, an SMS code reaches a real Indian handset, and `messageOutbox` rows read `sent` with a
`providerMessageId`. A `200` from MSG91 is not delivery.

### The DLT path, as MSG91 described it

1. Sign up at **smartping.live**; upload PAN, GST, ID proof, address proof and the signed Letter
   of Authorisation. Write **"Referred by MSG91 (Walkover)"** in the remarks.
2. Verify by OTP on mobile and a link by email (check spam).
3. SmartPing approves the documents and sends the ₹5,000 + GST payment link. The 19-digit

4. **PE-TM chain binding — compulsory since 11 Dec 2024; without it nothing is delivered.** Add

5. **Header:** register `SAHATX`, then add it in the MSG91 panel with the Entity ID. ~24 h to sync.
6. **Templates:** register on DLT (2–4 working days), then add each in the MSG91 panel with its

## 5. Phases

### Phase A — account basics (the owner's)

Sign in; if a login OTP is needed, stop and ask. Locate KYC and the wallet, report exactly what
each asks for, and **stop**. Continue only when the owner confirms KYC has cleared and the wallet
is funded.

### Phase B — auth key

Find the API key section and report what key types the account offers (this is also the practical
answer to Q26 — report what you actually see). Generate a key, write it into `apps/api/.env` as
`MSG91_AUTH_KEY=…`, and confirm only that the line was written. **Do not set
`NOTIFICATION_PROVIDER` yet** — §7 explains why that would break the local stack.

### Phase C — email domain

Add the domain the owner nominates — **ask; do not assume a subdomain** (Q29). Report the DNS
records MSG91 asks for (SPF, DKIM, MX, return-path CNAME) **verbatim**; the owner adds them at the
DNS host. **Flag loudly if MSG91 asks for an MX record on the root domain** — that would collide
with Google Workspace and must not be added. When the owner says DNS has propagated, run
verification and report the result.

Then set the four sender addresses in `apps/api/.env` — there is no single `MSG91_EMAIL_FROM` any
more. One per Communications group, chosen by template key
(`communicationGroupForTemplate` in core):

| Variable                     | Address                         | Group                            |
| ---------------------------- | ------------------------------- | -------------------------------- |
| `MSG91_EMAIL_FROM_ACCOUNT`   | `no-reply@sahatextile.com`      | sign-in and verification codes   |
| `MSG91_EMAIL_FROM_ORDERS`    | `orders@sahatextile.com`        | order updates                    |
| `MSG91_EMAIL_FROM_SHOP`      | `notifications@sahatextile.com` | back in stock, question answered |
| `MSG91_EMAIL_FROM_MARKETING` | `newsletter@sahatextile.com`    | sale and launch, newsletter      |

All four are aliases of `wecare@sahatextile.com`, so replies land in the customer-care mailbox.

### Phase D — email templates are created through the API, not the console

Owner decision, 17 Nov (route B): the 24 email templates are **our own designs, written in MJML,
kept in our code, and registered with MSG91 through `POST /api/v5/email/templates`** (`name`,
`slug`, `subject`, `body`). The send API takes `template_id` + `variables` and has no HTML field.
**Do not hand-build these in the console.** Codex's job here is only to confirm the account can
create templates by API and to report their approval status — the HTML itself is repo work.

Constraints already established: Handlebars supports `{{#each}}`, `{{#if}}`/`{{else}}`,
`{{#unless}}`, dot paths and `@root` — **no `and`, `or`, `gt`, `eq` or `length`**, so our API sends
ready-made yes/no flags. An approved template cannot be edited; "Copy as Version" makes a new draft
under the same id. Gmail clips HTML over 102 KB.

### Phase E — DLT phase 1 (SmartPing)

Walk §3 steps 1–4. **Fill nothing** on the entity form — report the document list and stop. After
entity approval, apply for `SAHATX` (ask the owner whether Q11 came back: once, or once as "Other"
and once as "Promotional"). After header approval, submit the **18 SMS content templates from the
20 Nov document** — but only once the owner confirms MSG91's review has arrived (§4).

### Phase F — DLT phase 2 (MSG91 panel)

Map the Entity/PE ID and the approved header. Complete the PE-TM chain binding with Walkover's
TM ID. Create the MSG91 SMS templates, each carrying its approved DLT Template ID. Record every id.

### Phase G — the `flow_id` vs `template_id` question

`packages/adapters-notifications-msg91/src/tools/sms-flow.tool.ts` carries a
`⚠ PENDING LIVE VERIFICATION` note: MSG91 renamed Flow → Template across v5 and their API
reference sits behind a login, so the code deliberately sends **both** keys with the same value.
Their public help pages do not settle it. The first successful SMS does. Report which key the
account honoured if the response reveals it — **do not edit the code.**

## 6. Templates — use the document, never this file

The authoritative list is **`.claude/Saha Textile - message templates (updated 20 Nov).docx`**:
18 SMS content templates, 1 consent template, 24 email templates, each with final wording, DLT
category, variable tags in order, and character count. Open it and register from it.

This file deliberately does **not** restate the wording — a second copy is a second source of
truth, and the one thing DLT punishes hardest is text that does not match character for character.

Two rules from the code that will silently break delivery if broken:

1. **Variable names are fixed by the sender.** The API sends `variables: { code }` for OTPs — the
   placeholder must be `code`, not `otp`. Likewise `token`, `field`, `maskedNewValue`, `role`.
2. **Email `template_id` resolution.** `resolveProviderTemplateId` returns the template's own key
   for email and `dltTemplateId` for SMS. Q35 (is `template_id` the slug returned at creation?) is
   still unanswered — confirm before the first send.

## 7. Cutover and proof

Only after templates exist on both sides, and only with the owner's go-ahead:

1. **Remove `OTP_LOCAL_FIXED_CODE` from `apps/api/.env` first.** The config **fails closed**: it
   refuses to boot when that variable is set and `NOTIFICATION_PROVIDER` is anything but `console`
   (`app-config.ts:477`). Flip the provider with the fixed code still present and the API will not
   start. This is deliberate — it stops a real provider ever delivering a predictable code.
2. Insert the matching `notificationTemplates` rows in Mongo. **Nothing seeds this collection**;
   the adapter refuses to send without a row, so every send would fail with "Notification template
   missing or channel mismatch". Ask the repo owner whether a seeder has landed.
3. Set `NOTIFICATION_PROVIDER=msg91`.
4. **Restart the API.** `nest start --watch` watches `apps/api/src` only; it neither reloads `.env`
   nor picks up a rebuilt workspace package. A test against a stale process proves nothing.
5. Trigger one real email OTP through the storefront signup form; confirm arrival in a real inbox.
6. Once DLT is live, the same for SMS on a real handset.
7. Read the outbox:

    ```bash
    docker exec saha-textile-mongo mongosh --quiet --eval '
    const d = db.getSiblingDB("saha_textile_local");
    d.messageOutbox.find({}, {_id:1, channel:1, templateKey:1, status:1, providerMessageId:1, errorMessage:1})
      .sort({createdAt:-1}).limit(10).forEach(printjson);'
    ```

    `sent` with a `providerMessageId` passes. MSG91 error 211 = missing or invalid DLT template id;
    203 = PE ID missing or header not approved.
