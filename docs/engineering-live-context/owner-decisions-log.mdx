### UI reuse and the pre-build brief (`DEC-UI-REUSE` — locked 2026-08-11)

Reusing what already exists is a hard rule, not a preference. Every screen — new or existing —
is assembled from elements and CSS classes the repository already has. Sources, in order:
the app's own `shared/ui` and feature templates; pruned or deleted pages still recoverable
from git; and `vendor/` (Fastkart), which carries elements no live page currently uses.

Three ways to reuse, all permitted, chosen by fit:

1. use the existing element unchanged;
2. copy it under a different name prefix and modify the copy, when two callers need genuinely
   different behaviour and one shared component would serve neither well;
3. promote it to a shared component when several callers need it identically.

**Before writing anything custom — always, proactively, and whether the custom work was asked
for or merely follows from an unrelated task — stop and give the owner a brief containing:**

- what changes, in crisp bullets;
- a wireframe (SVG, image or rendered mockup) of the proposed layout;
- the conditional logic the screen will apply;
- an explicit inventory of the existing elements and CSS classes being reused;
- an explicit statement of what, if anything, is genuinely custom — and if the answer is
  "nothing", say that plainly, because it is the claim the owner is approving;
- anything already built that the change makes redundant.

Then wait for approval. If custom work turns out to be unavoidable once building has started,
stop again and show it in the browser pane for verification before it lands. A silent new CSS
class, element or component is the failure mode this rule exists to prevent.

## Catalog, products, categories, and search

- Categories use a multi-placement DAG through category placements; do not force a strict single-parent tree.
- Imported WooCommerce category junk is cleaned rather than preserved as target truth.
- Product model supports:
    - simple products;
    - SKU/variation products;
    - tailoring/customization;
    - related/cross-sell/upsell relationships;
    - true bundle/composite products.
- Product option semantic roles are independent of display style.
- Semantic roles:
    - `filter_only`;
    - `variation_axis`;
    - `named_add_on`;
    - `bundle_component_option`.
- An option is a variation axis only when it changes SKU, stock, price row, image, base identity, or purchasability.
- Color, size, fabric, design, waist, liter, and other axes are product-specific toggles; none is globally variation-driving.
- Canonical display styles:
    - `rectangle`;
    - `circle`;
    - `image_swatch`;
    - `color_swatch`;
    - `radio`;
    - `dropdown`;
    - `image_tile` (“Image V2”);
    - `radio_bar`.
- `image_tile` and `radio_bar` were added for storefront/admin renderer parity and are part of the canonical set; the earlier “canonical six” wording predates them (confirmed 2026-07-31, reconciled against `packages/contracts/src/attribute.ts`).
- Visual display style never determines business behavior.
- A standalone blouse may use design as a variation axis.
- A saree’s included blouse piece remains part of the base saree; `Blouse Design` is a named add-on group with `No Design` default and optional pricing/media/measurement requirements.
- Multiple named add-on groups are supported.
- Bundle/composite products cannot contain another bundle; nesting is disallowed (`DEC-BUNDLE-NESTING`).
- Product primary statuses are `draft`, `live`, `disabled`, and `discontinued`; only `live` products are storefront-queryable across listing, search, and sitemap.
- `disabled` hides a product from all storefront surfaces while retaining its full data and media (reversible).
- `discontinued` hides a product and starts a 30-day retention window; after it, rich data and Spaces media are purged, leaving a minimal tombstone (name, SKU, audit references).
- Historical order lines keep their immutable purchase-time snapshot; purged product media falls back to a single global placeholder image in order views.
- In order views, links to disabled, discontinued, or purged products are non-navigable: muted styling, no pointer cursor, and a reused theme tooltip reading “no longer available”.
- Search uses self-hosted Meilisearch behind `SearchPort`.
- MongoDB is source of truth; Meilisearch is a rebuildable denormalized index.
- Launch search surface includes typo tolerance, aliases, transliteration support, suggestions, no-result analytics, and admin dictionary tuning.
- Category/listing facets come from Meilisearch through `SearchPort`.
- Category/placement facet configuration controls public filters, order, style, counts, and mobile/desktop visibility.
- Arbitrary faceted URLs are `noindex,follow` and canonicalize to the base listing unless explicitly modeled as SEO landing pages.

## SKU generation (`DEC-SKU` — locked)

- Product and variant SKUs are globally unique.
- A SKU is an admin-defined prefix plus a per-prefix auto-incrementing counter; variant SKUs are auto-suffixed from the product SKU.
- A category may define an optional default SKU prefix that prefills the product SKU and is overridable per product.
- On manual override, a multi-category prefix conflict, or any prefix validation failure, the product form blocks and requires resolution: if the entered prefix already exists, the admin confirms either a different prefix (its counter starts fresh) or continuation of the existing prefix's counter.
- The same conflict/verify workflow covers products placed in multiple categories and categories with multiple DAG placements that carry differing prefixes; it mirrors the HSN mismatch workflow.
- A SKU is immutable once its product/variant is published or referenced by any order; changes are audited.

- Selling/catalog prices are stored and displayed tax-inclusive.
- Tax-exclusive bases are reverse-calculated only where invoices/reporting require them.
- Inventory valuation uses FIFO cost layers.
- FIFO/COGS details are never customer-facing.
- Manual inventory adjustments require a fixed reason code:
    - `damage`;
    - `lost_missing`;
    - `manual_recount_correction`;
    - `supplier_shortage`;
    - `return_restocked`;
    - `return_not_restocked`;
    - `internal_use_sample`;
    - `photoshoot_display_use`;
    - `system_migration_correction`;
    - `other`.
- Notes are optional for the first nine and mandatory for `other`.
- Orders, payments, shipments, returns, and refunds are separate collections connected by durable identifiers.
- Order lines are immutable purchase-time snapshots.
- Multi-document commerce writes use MongoDB transactions.
- Weekly analytics produce persisted insight sets and stable badge assignments; storefront cards/rails do not run live analytics joins.

## Cart, pending intents, and offline behavior

- Guest add-to-cart is available.
- Guest checkout is not available at launch.
- `Proceed to checkout` forces login/signup, merges the guest cart, then resumes checkout.
- Guest carts are server-authoritative and stored in `carts`.
- Guest identity uses an opaque random `st_guest` httpOnly cookie; only its hash is stored server-side.
- Guest cart TTL is 30 days sliding from last activity.
- Guest-to-user cart merge is transactional.
- Invalid/unavailable merge lines are reported, not silently dropped.
- Pending intent stores one latest account-bound action per guest/session.
- Pending-intent TTL is at most 30 minutes unless a feature requires less.
- Auth success order is:
    1. merge guest cart;
    2. revalidate pending action;
    3. replay if allowed;
    4. clear intent;
    5. return to the relevant continuation.
- Wishlist and Save for Later are separate account-bound concepts.
- Notify Me is account-bound and product/variant-aware.
- Product Q&A does not require login.
- Reorder/Buy Again is already an authenticated flow and is not a pending intent.
- Public track order is not available at launch.
- When built later, track order requires order number plus matching email or phone, with rate limits and anti-enumeration.
- IndexedDB/Cache Storage are browser-side cache/queue mechanisms, never backend infrastructure or source of truth.
- Offline mode covers previously cached public catalog plus offline cart mutations.
- Never cache auth tokens, refresh tokens, payment data, admin data, or account/order PII offline.
- Storefront privacy UI exposes a clear-local/offline-data action.

## Authentication, sessions, and admin security

- Browser authentication uses API-set httpOnly/Secure/SameSite cookies.
- Use double-submit CSRF, short access lifetime, opaque rotating refresh tokens, and refresh reuse detection.
- Browser happy path is cookie-first; bearer support is limited to approved non-browser clients.
- Password minimum is 12 characters for storefront and admin, with a common-password denylist.
- Storefront auth supports email/password, Google, Facebook, and channel-direct email OTP.
- X/Twitter login is excluded.
- ~~Phone is collected at checkout/address stage, not registration.~~ **Superseded 2026-08-16 by
  `DEC-SIGNUP-VERIFICATION`:** phone is now collected AND OTP-verified during registration, and
  is a first-class login credential. The original lock predates the decision to make every
  account carry two proven channels; it is struck rather than deleted so the reversal is visible.
- Phone OTP remains a seam until enabled through the notification provider.
- OAuth UI uses provider JS buttons/One Tap where appropriate; the backend verifies provider tokens and owns the Saha Textile session.
- Minimum provider scopes only.
- Admin has no mandatory MFA at launch; preserve the seam.
- Admin supports email-or-username plus password.
- Admin may configure a six-digit PIN:
    - optional during onboarding;
    - always available in Security Settings after password proof;
    - usable for full login and idle quick-resume;
    - preferred method is `password` or `pin`;
    - weak, repeated, and sequential PINs are rejected;
    - five failed PIN attempts lock PIN use for 15 minutes or until password login;
    - PIN is password-grade hashed and audited.
- Admin inactivity uses a 15-minute soft lock while preserving the mounted route/form state.
- Soft-lock is a **presence proof** (PIN/password resume). Admin **server session idle** is a
  separate hard kill and must outlive soft-lock so resume can rotate a still-live session
  (locked 2026-08-14: soft-lock 15m, admin idle TTL 60m, absolute 12h). Access JWT remains
  short-lived; soft-lock/visibility refresh keeps cookies usable without unlocking the UI.
- Password, role, permission, account-status, token-version, and reuse-detection changes invalidate quick resume.
- Protected admin deep links resume after successful login.
- RBAC failures are never queued or replayed.
- Object-level authorization is mandatory for owned resources.

### Account separation (`DEC-ACCOUNT-SEPARATION` — locked 2026-08-12)

This lock **amends** the previously ratified single-`users` model in the auth build prompt
§8 target list and the security matrix §1 collection table. Storefront customers and
back-office operators are distinct populations. Implementation follows
`account-separation-task-handoff.mdx`.

| Concept              | Physical collection | Contract entity | Id prefix |
| -------------------- | ------------------- | --------------- | --------- |
| Storefront shopper   | `customers`         | `Customer`      | `cus_`    |
| Back-office operator | `adminUsers`        | `AdminUser`     | `adm_`    |

Prose and comments keep saying “operator”; identifiers say `adminUser`. The bare noun
“user” must not name either population.

- **D1** — The same email **may** exist in both collections. Uniqueness is **per
  collection**. Every identifier lookup, password reset, OTP challenge and registration is
  population-scoped. Anti-enumeration treats “exists only in the other population” as
  unknown.
- **D2** — Operators keep a coarse role of `staff` | `admin`. Fine-grained permissions
  remain authoritative. This lock is account separation, not an RBAC rewrite.
- **D3** — `/admin/users/**` and the admin User screens administer **operators only**.
  Customer CRM is a later `/admin/customers/**` surface with new `customer.*` permission
  codes. Existing `user.*` codes keep meaning operators for this task; renaming them to
  `admin_user.*` is a follow-up with the account-naming lint, not part of the split.
- **D4** — `assertOwnership` is **id-equality only**. Support-read of a customer order or
  cart requires admin audience **and** a permission (`order.index` for orders; a new
  server-only `cart.index` for carts). It is not a coarse-role bypass.
- **D5** — Id prefixes are `cus_` (customers) and `adm_` (operators). The irreversible
  split rewrites moved operator ids and every foreign key that pointed at them. The audit
  read model tolerates leftover `user_` rows as unknown-population.
- **D6** — Local identity/auth collections are wiped and the first administrator is
  re-bootstrapped. The disclosed `owner@saha-textile.test` password is not migrated. The
  split script is still built and integration-tested against fixtures. Catalog and commerce
  data stay.
- **D7** — A customer document has **no** `role` field. `UserRole` becomes `AdminRole` =
  `staff` | `admin`. Storefront sessions carry `audience` only; `roleAtLogin` remains on
  admin sessions.
- **D8** — An operator **may** hold a personal storefront account. It is **unlinked**:
  separate credentials, no foreign key. Combined with D1, the same email may exist on both
  sides as two people in the system.
- **D9** — Shape the customer document for known account data now: typed named addresses
  (existing `Address` contract plus a `label`; do not add billing-vs-shipping policy flags
  that would close `DEC-ADDRESS`), plus reserved empty typed arrays `contacts`,
  `savedSizes` and `measurementProfiles` (no routes write them in this task; measurement
  keys stay open under `DEC-ADDON-MEASUREMENTS`). Do **not** embed wishlists, orders,
  carts, sessions, tokens, consent history, or a link to `adminUsers`. Embedded password
  hashes remain until the already-ratified credential-collection extraction; freezing them
  onto `customers` would cancel that security destination.
- **D10** — Rename `users` → `customers` (reversible aligner), then split operators into
  `adminUsers`. Both new names take a temporary `NON_GRAPH_COLLECTIONS` exception until the
  portal tool reconciles Schema Nebula. The graph file and portal-derived docs stay out of
  scope for the split task.
  **Status 2026-08-13:** Schema Nebula reconciled (`customers` + solid `adminUsers`, graph
  **65 / 32 / 33**); the temporary `NON_GRAPH` exceptions for those two names are cleared.
  Remaining NON_GRAPH: `authRateLimits`, `productQuestions`, `ratingAggregates` only.

## OTP and notifications

- `NotificationPort` is the customer-messaging boundary.
- MSG91 is the primary customer notification provider for email, SMS, and WhatsApp.
- Resend/SES/SMTP may exist only as optional email fallback adapters, never primary.
- Team mailboxes use Google Workspace and are separate from programmatic messaging.
- OTP is generated, stored, and verified by Saha Textile; do not use MSG91 OTP Widget or SendOTP.
- OTP code:
    - CSPRNG six digits;
    - HMAC-SHA256 with server pepper at rest;
    - 10-minute expiry;
    - maximum five attempts;
    - single active challenge per identifier and purpose;
    - atomic consume and attempt updates;
    - never logged.
- OTP send responses are generic and anti-enumerating.
- Notification kill-switches are split by channel and category:
    - transactional/utility;
    - marketing.
- Disabled channel/category combinations short-circuit before calling providers.
- Marketing sends require consent and approved templates where applicable.
- Usage thresholds, spend warnings, auto-disable behavior, RBAC, and audit are required.
- **2026-08-13 owner lock (Authkey placement):** MSG91 Authkey lives in API env (`MSG91_AUTH_KEY`) only.
  Admin Settings may manage kill-switches, plan limits, and non-secret template/Flow/WhatsApp ids —
  never paste or display the Authkey. Sender/from/WhatsApp number remain env for now.

## Audit and retention

- Every admin mutation writes an audit record.
- Explicit coverage includes catalog, price, stock, purchase invoice, order, payment/refund, shipping/tax/payment/currency/notification config, role/permission, login failure, session revocation, and security events.
- Financial/security audit retention is seven years.
- Catalog/general-admin audit retention is five years.

- Prefer bounded field diffs over unbounded before/after blobs.

### Deletion and retention (`DEC-DELETE-RETENTION` — locked)

- Durable business records (catalog, orders, invoices, payments, returns, credit notes, customer accounts, gift cards, ledgers) are soft-deleted — recoverable and filtered from active queries — never hard-deleted, subject to the financial/audit retention windows above.
- Transient security and session records (sessions, OTP challenges, rate-limit counters, pending intents, guest-cart handles) use TTL expiry.
- Hard deletion is reserved for explicit privacy/legal purge requests and for orphaned media after a grace period; the discontinued-product 30-day rich-data purge is a defined exception that still preserves a minimal tombstone plus order snapshots.

## Storefront signup, social identity, and OTP (`DEC-SIGNUP-VERIFICATION` — locked 2026-08-16)

Supersedes "phone is collected at checkout, not registration" (2026-06-29, struck above).

**Nothing is created before it is proven.**

- A customer row is created only after email AND phone are OTP-verified. There is no
  unverified account state, which removes the pre-hijack takeover class outright: an attacker
  cannot squat an address they do not control and wait for the real owner to arrive.
- Verified state lives in a server-held **pending-signup document**, keyed to the session,
  holding the exact verified values, the consent selections, the guest-cart token and any
  social provider id. Final submit uses the STORED values and never the posted ones — a client
  that could assert "this email is verified" is a forgery waiting to happen.
- Sliding TTL: 15 minutes, extended on each verification or send, absolute cap 30 minutes.
  Abandoned records expire and are deleted. A pending record does **not** reserve an email or
  phone; uniqueness belongs to real customers only, so nobody can hold addresses hostage.
- Fields stay editable after verification. Editing clears that field's verified flag and
  re-arms its verify control. Locking a typo'd address in buys no security, because the
  verification is bound server-side to the value.

**Disclosure: prove control, then we'll talk.**

- Requesting an OTP never varies its response and never reveals existence. Delivery is
  enqueued to `messageOutbox` in every branch, so a non-existent account spends no credits
  AND the response time is identical — skipping the send synchronously would leak in the
  timing dimension what the message no longer leaks in words.
- Once OTP succeeds — or Google asserts `email_verified` — the person has proven control, and
  disclosure to them is safe and helpful. They are offered sign-in or start-over; sign-in is
  granted directly, because the OTP already served as the proof.
- Facebook's email is never proof on its own. The Facebook path always requires our own email
  OTP, whether Meta supplied an address or not; prefill when given, blank when not.
- Password login failure is one message, always — regardless of whether the account exists,
  has no password, or has three providers linked.
- Auto-sign-in is refused for `disabled`/`locked` accounts with a contact-support message.

**Social identity.**

- Identities are keyed on provider + stable subject: Google `sub`, Facebook app-scoped id.
  **The Facebook id is scoped to the app** — the DEV app and a future production app issue
  different ids for the same person, so development ASIDs do not survive to production.
- Accounts are never auto-linked on a matching email. Linking is deliberate, from the profile,
  and requires step-up: the password when one is set (free and stronger), otherwise an OTP
  with the customer choosing email or phone.
- Connecting an identity already linked to another customer is a clean refusal, not a
  duplicate-key error.
- Disconnect enforces that at least one usable credential remains.

**Phone as a login credential.**

- Phone OTP is a full login, equivalent to any other. **Accepted risk, owner-decided:** Indian
  carriers reassign numbers after roughly 90 days, so whoever inherits a recycled number
  inherits the account. Recorded rather than mitigated, deliberately.
- Changing an email or a phone still requires recent credential proof and verification of the
  new value before the old one is released (matrix row 84) — a separate control from what a
  phone OTP may authenticate.

**OTP abuse limits** — numbers live in `rate-limit-policy.ts`, windows configurable.

- The sharp control is the DESTINATION address (the existing `identifier` scope), not the IP:
  5 email + 5 SMS per pending signup; 5 combined per account for sign-in, forgot-password,
  change-password and connect-social.
- IP ceilings stay deliberately loose as a flood stop only, keyed through
  `rateLimitClientScope` so IPv6 is counted per `/64` while IPv4 is treated as coarse —
  Indian consumer internet is carrier-grade NAT, and a tight per-IP limit locks out a town.
- Resends use progressive backoff rather than a hard cliff, so an honest mistake never costs a
  full window.
- Connect-social lets the customer choose the channel before generation, so a non-essential
  action cannot silently spend SMS credits.

**MSG91 delivery.** Unchanged and already locked: Saha Textile generates, stores and verifies
every OTP; MSG91 is delivery only, never the OTP Widget or SendOTP.

## Storefront account & auth UI (owner lock 2026-08-18)

**Remember me is real, not decoration.** Ticked → dated cookie plus the 30-day idle TTL;
unticked → a session cookie plus a ONE-DAY idle TTL. Both halves move together: shortening only
the cookie leaves a captured refresh token honoured for the full month. Rotation carries the
choice, so a refresh never silently promotes a browser session to a remembered one. Operators get
no such control — the hour-long admin idle bounds them either way.

**Provider buttons are the providers' own.** Google's `renderButton()` (never a hand-drawn
imitation), and a Facebook button built to Meta's published guidance because Meta ships no
drawable widget. Both capped to Google's 400px ceiling so the pair is the same length.

**A storefront customer has no permissions.** Permissions are operator vocabulary that arrived
with the vendor port. A customer's access follows from owning the account. The storefront store's
`permissions` state is deleted rather than left empty, so nobody starts gating on it.

**`account.json` is retired.** Account screens read the signed-in customer from
`/auth/storefront/me`. Wallet, loyalty points, order count, payout details and avatar are shown as
zero/absent rather than carried over — they are separate features that do not exist, and a balance
is the closing position of a ledger, not a number on the account row.

**Self-service routes never name another account.** Everything under `storefront/account/*`
takes its owner from the session; there is no `:customerId` in any path. Operator equivalents stay
under `admin/customers/:customerId/*` and are authorised per permission. Two surfaces, and neither
can be mistaken for the other.

**Address pickers resolve country FIRST**, then state within that country, then the dial code from
the country record. A dial code does not identify a country (`+1` is the USA, Canada, American
Samoa and most of the Caribbean) and neither does a state code (`TN` is Tamil Nadu and Tennessee).

**Profile self-service is display name only.** Email and phone are login credentials; changing one
requires the security matrix's row-84 flow rather than a patch field, so a stolen session cannot
move an account's recovery channel in one request.
