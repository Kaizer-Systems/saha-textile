## Cross-cutting invariants

- Angular never connects to MongoDB, Meilisearch, Spaces, or providers directly.
- `packages/contracts` owns shared Zod shapes.
- Core may consume contract shapes through `import type` only and stays runtime-pure.
- MongoDB is self-hosted 8.3 with replica-set transactions.
- MongoDB is source of truth; Meilisearch is derived and rebuildable.
- Canonical price is INR and final money math runs server-side.
- Browser auth uses cookies plus CSRF; no browser token happy path.
- Object-level authorization is mandatory.
- Admin mutations are audited.
- Provider integrations remain behind ports.
- Production providers wait for approved credentials and current official documentation.

### Chunk D — Identity, sessions, OTP, OAuth, PIN, privacy

**Marker:** SAFE NOW for locked mechanics; SEAM NOW for optional future methods

#### Pass boundary

- **D1 — auth persistence (done):** tested session, OTP, OAuth-state, reset-token,
  verification-token, admin-invite, role, user-role-assignment, and auth-rate-limit
  repositories/models; secret fields excluded by default; atomic consume/rotation,
  rate-limit and unique-active-assignment mechanics proven against rs0. Explicit
  physical names now align every target-backed model with the locked camelCase Schema
  Nebula graph. `authRateLimits` remains intentional current adapter evidence outside
  that graph. Persistence capability alone does not prove HTTP adoption.
- **D2 — session lifecycle (done):** issue, refresh, revoke, refresh-reuse family
  revocation, session-bound CSRF, and storefront/admin audience guards are implemented
  and live-proven through httpOnly cookies.
- **D3 — storefront auth endpoints (done):** register, password login, logout, me,
  refresh, password reset, email-verification completion/resend, and OTP use generic
  anti-enumeration responses. Google and Facebook sign-up/sign-in were proven end to end
  with the owner's real provider accounts on 2026-10-25.
- **D4 — admin auth (done):** password/PIN login, password recovery, PIN
  setup/lockout, invite create/list/revoke/acceptance, HTTP quick-resume, audience guards,
  and permission-version invalidation exist. The closed **103-code** permission registry,
  active role-assignment resolution, deny-by-default role/permission/user-authority routes,
  no-delegation-above-self, last-administrator protection, audited offboarding, and the
  operator-only first-administrator bootstrap are implemented and negative-tested. Account
  Security at `/account` (PIN/password/sessions) and the 15-minute idle soft-lock
  (`IdleLockService` + `idle-lock-modal` + `POST /auth/admin/resume` with PIN or password)
  are live. A real browser has proven password login, cookie-only reload, refresh recovery,
  role grant/revoke, permission invalidation, last-admin refusal, and logout. On 2026-11-03
  the admin accept-invitation page (`/auth/accept-invite`) was added and a real browser proved
  invite → acceptance (weak PIN refused without spending the invite) → PIN sign-in → wrong
  PIN → five-failure lock refusing even the right PIN → password sign-in clearing the lock.
  Route migration is complete: `check-route-authorization` (in `pnpm lint`) holds every route
  to a permission or a written self-service justification.
- **D5 — consent, privacy, and ownership (done for this chunk):** consent history, export/erase
  seams, order-read BOLA, cart ownership/`st_guest` proof, and order-create cart
  ownership/adoption are implemented. Cart routes remain `@Public()` for guest
  add-to-cart but enforce Principal/guest-token proof in the service boundary. Guest→user
  merge, pending intents, and checkout idempotency remain Chunk G.

**Chunk D is done (2026-11-03, owner-confirmed).** Guest→user cart merge, pending intents
and checkout idempotency are carried by Chunk G, which owns the cart and checkout they act on.
The 2026-08-11 reassessment that kept D partial predates the real-account OAuth run, the
accept-invitation page and the browser PIN proof.

#### Deliver

- Cookie session issue/refresh/revoke/reuse detection.
- CSRF enforcement.
- storefront/admin audience guards.
- password, reset, email verification, OTP challenges.
- Google/Facebook backend verification.
- admin invite, PIN setup/login/lockout/quick-resume.
- consent state/events and privacy export/delete seams.
- role, permission-version, token-version, and ownership authorization.

#### Definition of Done

- Auth/session/CSRF/audience/ownership tests pass.
- Tokens never appear in browser response bodies or logs.
- Generic anti-enumeration behavior is tested.
- Admin and storefront sessions cannot cross audiences.
