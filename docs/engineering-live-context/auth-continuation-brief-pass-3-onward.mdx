## 2. What is actually true now (verify before trusting)

### Persistence

- All **32** Mongoose schemas declare an explicit `collection` name matching the ratified
  64-node Schema Nebula graph. `packages/adapters-db-mongo/src/collection-names.ts` is the
  single declaration; `test/collection-names.test.ts` asserts every model against it and
  reads `docs/_data/instruments/schema-nebula.json` directly.
- `pnpm mongo:align-collections [-- --dry-run]` migrates a legacy database. Idempotent,
  refuses to merge when both names hold data, no `dropTarget`, never runs at boot.
- `authRateLimits` is intentionally outside the 64-node graph. `productQuestions` and
  `ratingAggregates` are implemented models with **no node in the graph** — an open
  documentation gap, not a licence to rename them.

### API

- Cookie-only sessions. `SessionGuard` is global; routes opt out with `@Public()`. It reads
  the access token from the httpOnly cookie ONLY — bearer is ignored everywhere.
- `CsrfGuard` is global and fails closed on unsafe methods when session cookies are present.
- `@Audience('storefront'|'admin')` enforces surface isolation.
- Admin password recovery is complete: `POST /auth/admin/password/forgot` and
  `POST /auth/admin/password/reset`, audience-bound, with `users.pinRevalidationRequiredAt`
  suspending PIN use until a successful password login (cleared inside
  `recordSuccessfulLogin`, so no caller can skip it).

### Angular clients

- **No fake token, no bearer header, no session in browser storage, no demo credentials, in
  either app.** Enforced mechanically by `scripts/check-browser-auth.mjs` in `pnpm lint`.
- Each app owns one typed auth gateway (`core/auth/auth-gateway.ts` abstract class as DI
  token) and exactly one HTTP adapter (`core/auth/http-auth.gateway.ts`) holding route
  paths. Components, guards and stores depend on the gateway, never `HttpClient`.
- Stores are session facades with a three-valued status: `unknown` / `anonymous` /
  `authenticated`. `unknown` must not be collapsed into `anonymous` — that bounces a
  signed-in user to login during hydration.
- Session resolves before routing via an app initializer that awaits `runtimeConfigReady`
  (Angular starts initializers concurrently; registration order is NOT ordering).
- Storefront bootstrap is browser-only by design: SSR has no cookie jar and must not render
  a per-user account shell.

## 5. Gotchas that will otherwise cost you an hour each

1. **`pnpm validate` does not exist at root.** §13 of the build prompt names it; the real
   gates are in §6 below.
2. **Turbo caches tests.** Use `pnpm turbo run test --force` for a real run.
3. **Adapter integration tests are opt-in:**
   `MONGODB_PORT=27018 RUN_DB_IT=1 pnpm --filter @saha-textile/adapters-db-mongo test`.
   Without those vars 85 of 89 silently skip.
4. **`apps/api` `pnpm start` runs `node dist/main.js`.** Always `pnpm --filter
@saha-textile/api build` before probing, or you will measure a stale `dist`.
5. **Angular apps have no Node types, correctly.** A test needing `node:fs` cannot live in
   `apps/*/src/**/*.spec.ts` — the Analog Vite plugin fails to transform it. Repo-policy
   scanners belong in `scripts/*.mjs` wired into `pnpm lint`, like `check-browser-auth.mjs`.
6. **`import.meta` is illegal in `adapters-db-mongo`'s CommonJS output.** Resolve paths from
   `process.cwd()` with an assertion instead.
7. **Never `JSON.parse`/`stringify` an i18n file.** It reorders numeric-like keys and
   retabs the whole file. Append entries textually; validate by parsing afterwards.
8. **CSRF on probes:** an unsafe request carrying session cookies needs the `x-csrf-token`
   header matching the readable `st_csrf` cookie, or you get `403` and will misread it as an
   auth failure. Read it with `awk '/st_csrf/{print $7}' cookiejar.txt`.
9. **Every 401 looks the same to a client** (see PIN sub-code above). Do not write
   client-side branching on 401 detail — it will be dead code.
10. **There is no first-admin bootstrap.** To probe admin flows, insert a user document
    directly with `role: "admin"`, `status: "active"`. For a reset-token probe, derive the
    hash yourself: `HMAC-SHA256(token, pepper)` where
    `pepper = CSRF_SECRET || JWT_REFRESH_SECRET` from `apps/api/.env`. Never print the
    secret. **Always delete probe rows afterwards** and confirm `users` count returns to its
    prior value.
11. **`rm -rf` is blocked by the permission classifier.** Use `git rm`, then `git reset` to
    unstage — `git rm` stages the deletion, and staging is not allowed here.
12. **`check-browser-auth.mjs` strips comments before matching**, so documenting a forbidden
    pattern is safe. `browser-auth:allow` on a line is the deliberate opt-out.
13. **The Browser pane can stop compositing frames** mid-session and not recover. Fall back
    to a built-bundle scan (`grep -rlF` over `apps/*/dist/**/*.js`) plus unit tests, and say
    plainly in the progress entry that browser E2E did not run.
14. **Matrix §1 is verbatim approved text.** Record implementation reconciliations in §2
    (the addendum), never by editing those tables. §2.5 is the precedent.

## 7. Non-negotiables carried forward

- Hexagonal layering. Core imports no NestJS/Fastify/Mongoose/provider SDK. Adapters at the
  edges. Angular calls the API only.
- One HTTP auth adapter per audience; storefront code may not name an admin route and vice
  versa — enforced by `check-browser-auth.mjs`.
- No auth token in `localStorage`, `sessionStorage`, IndexedDB, URLs, analytics, logs, NgRx
  persisted state, service-worker cache or SSR response cache.
- Anti-enumeration: login, registration collision, OTP request and recovery answer
  identically for known and unknown identifiers. Never branch UI or routing on the outcome.
- Admin launch login methods are exactly: email-or-username + password; email-or-username +
  configured six-digit PIN; PIN quick-resume for an already-open session. No social login,
  no self-registration, no OTP login. The PIN is never described as MFA.
- Object-level authorization on every owned resource; `assertOwnership` throws **404**, not
  403, so an id cannot be probed for existence.
- Every admin mutation is audited; audit rows commit in the same transaction as the mutation.
- Never log or audit passwords, PINs, OTPs, cookies, tokens or provider payloads.
