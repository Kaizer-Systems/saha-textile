## 3. What this session delivered

### 3.1 Weak-PIN policy in core-domain — `1d3aba94`

`AdminPin` in contracts was a six-digit regex and nothing more, and its own comment had named
core-domain as the home of denylist/sequential/repeated rejection since the schema was written.
No such module existed, so `000000` and `123456` were acceptable administrator PINs.

`packages/core-domain/src/auth/pin-policy.ts` is pure and framework-free (the runtime-purity
suite still passes). Three rules:

- **repeat** — a repeating unit whose length divides six, so `777777`, `121212` and `123123`
  all fall to it: **1,090** PINs;
- **sequential** — a ±1 run counting around from 9 to 0, wraparound deliberate because
  `890123` is one finger motion exactly like `123456`: **20** PINs;
- **denylist** — **38** curated entries for what no structural rule catches: keypad columns and
  diagonals, grouped pairs and triples, famous constants, round numbers.

Total **1,148 of 1,000,000**, roughly one in 871. That number is asserted in the test suite
rather than described, because the policy's justification fails in both directions if nobody
knows it.

Enforced at both surfaces that can create a PIN, and the ordering at each is deliberate:

- `AdminSecurityService.setPin` checks strength BEFORE the recent-password proof — the verdict
  is a fact about a string the caller just typed and reveals nothing about the account, while
  Argon2 is deliberately expensive, so a caller cannot spend CPU by submitting `000000` in a
  loop;
- `AdminInviteService.accept` checks BEFORE `consume` — `consume` is atomic and single-use, so
  refusing afterwards would spend the invitation on a failed request.

The refusal travels as `validation_failed` with a stable `pin_sequential` / `pin_repeated` /
`pin_denylisted` / `pin_shape` issue code. `issues` is the ONLY channel `HttpExceptionFilter`
preserves — it replaces every message with a safe one chosen by status — and it is safe here
because both surfaces are authorized.

**Deliberately not rejected: date-shaped PINs** (`DDMMYY`, `MMDDYY`, a doubled year), the
largest real-world weak class. Rejecting all valid dates costs ~3.6% of the keyspace, and the
owner locked three named rules; a structural fourth is the owner's decision. Recorded as a
known omission inside the module. **The owner was asked and chose "leave it open for now" on
2026-08-11** — so it remains open, and the note in the module stays.

### 3.2 A failed recent-password proof answers 403 — `9e805553`

Found while wiring the gateway, and it had to be closed before any screen could call these
endpoints.

`requireRecentPasswordProof` threw `UnauthorizedException`. Both Angular interceptors read a
401 as "this session is gone": on a credential-classified route they clear the session store at
once; on any other route they rotate, replay, receive the same refusal and clear it anyway. So
a **mistyped current password would have signed the operator out of a session the server still
considers alive.** No route classification avoids it — both branches reach the same call.

403 is the correction rather than a workaround: the locked rule is 401 for an absent or invalid
session and 403 for a caller authenticated but insufficiently authorized, and somebody reaching
that line has a valid admin session and has failed a step-up for one operation.

The E2E asserts 403 with code `forbidden` and **no** `reason` field on all three proof
endpoints, that the session still works afterwards, and — the part that stops it being a
blanket downgrade — that the same routes still answer **401** with no session at all.

**The same question returns for storefront step-up, email change and set-password**, which the
matrix marks GOOD TO GO. It has not been applied there.

### 3.3 Security Settings gateway boundary — `88e8b956`

Four methods on `AdminAuthGateway` — `securitySettings`, `setPin`, `removePin`,
`changePassword` — plus `AdminSecurityState`, `AdminPinSetupInput`, `AdminPasswordChangeInput`.
Route paths live only in `http-auth.gateway.ts`, as `check-browser-auth` requires.

**None of the four is a credential route**, and that is pinned by tests rather than left to
intuition. Three carry a password proof, so the intuitive classification is "credential
endpoint" and it is wrong: a failed proof now answers 403 and never enters 401 recovery, so the
only 401 they can produce is a lapsed access cookie, which rotation SHOULD recover. Classifying
them otherwise would drop an operator at the login screen halfway through a credential change
because fifteen minutes passed while they typed.

The weak-PIN rule is deliberately NOT duplicated client-side; the gateway documents that the
server refuses and the screen renders the refusal.

## 6. Corrections, wrong turns and disproved theories

Recorded because the mistake is more instructive than the fix.

1. **The denylist redundancy test failed on its first run, correctly.** `696969` is `69` typed
   three times — already caught by the repeat rule — and so is `420420`. Both were removed. The
   two most-cited weak PINs are structurally weak; listing them would only have made the list
   look longer.
2. **`check-browser-auth` rejected my own test.** An audience assertion written as
   `path.startsWith('/auth/admin/')` is an auth path literal outside the one HTTP adapter. The
   prefix is now derived from the gateway's own `/me` route — compliant, and a stronger
   assertion.
3. **I asked the owner whether to extract the PIN keypad into a shared component. It was
   already shared.** `shared/ui/pin-pad` existed and login consumed it. The question was based
   on a wrong premise and wasted a decision.
4. **Angular class bindings defeated the theme's status pills, twice.** The theme styles them
   with `[class^='status-']` — a STARTS-WITH selector — and Angular writes static classes
   before dynamic ones however the dynamic one is expressed. Both `[class.status-x]` and
   `class="{{ … }}"` produced `class="d-inline-block me-2 status-pending"`, which never matches,
   and the pill rendered as a square box. The fix is a fully static class attribute per `@if`
   branch. **Only the browser caught this; no test would have.**
5. **The running API was 15h33m stale.** It served 52 paths with no `/auth/admin/security`,
   which produced a 404 and an error toast on the account screen while `dist` on disk was
   current. The process, not the build, was old. Restarted; 55 paths.
6. **I introduced a double toast.** `GlobalErrorHandlerInterceptor` already toasts every
   non-401 response, and my handler added a second. The server's specific reason now renders
   inline as `invalid-feedback` against the password field.
7. **I fired `/auth/admin/security` on page load**, over the Profile tab, for operators who
   never open Security. It now loads on tab activation.
8. **`pnpm e2e:session-rotation` differs by location.** The ROOT script runs
   `turbo run build --filter=@saha-textile/api` first; the same script inside `apps/api` does
   NOT. I briefly believed I had tested a stale `dist` and had to check. Run the root one.
9. **A `format:check` failure was masked by a pipe.** `pnpm format:check | tail -2` exits with
   `tail`'s status, so an `&&` chain continued and an unformatted commit landed. It was
   amended. Do not pipe a gate whose exit status you are relying on.
10. **Prettier's MDX parser broke `project-progress.mdx` twice**, both times by de-indenting a
    list continuation line — the generalisation of correction 7 in the pass-6 brief. Cause: an
    inline code span wrapped across a line break. Never let a code span straddle a newline in
    these documents.
