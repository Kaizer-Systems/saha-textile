# Admin application atlas

Filter the atlas before working on an operator workflow. A screen can look complete while its records and actions remain disconnected from the backend.

## Scaffolded capability criteria

For most admin feature families, scaffolded means:

- a lazy route exists;
- a standalone component and template exist;
- list/detail query functions exist;
- the service reads a typed JSON fixture;
- table/form interaction is present; and
- create/update/delete/approve/bulk behavior is absent, mocked, or navigation-only.

**Current exceptions (live, not fixture-only):** Account Security at `/account`; idle soft-lock resume; roles/operators authority; notification settings; CRM customers at `/customer`, `/customer/create`, `/customer/edit/:id` plus `/customer-ledger` against `/admin/customers/**` (soft-delete hides deleted by default; revive gated by `DEC-CUSTOMER-SOFT-DELETE-OPS`). Dial flags use HTML labels in `country-code.ts` and `/assets/images/flags/flags.png`.

## Operational readiness test

Do not call an admin workflow implemented until all of these are true:

1. The API contract is validated at the boundary.
2. Authentication uses the current cookie-session gateway and the API authorizes the operator/resource.
3. The API authorizes the action and target resource.
4. Reads and writes use real endpoints.
5. The UI handles pending, success, validation, conflict, failure, and retry states.
6. Audit/event requirements are satisfied.
7. Tests cover the critical operator path.
8. Portal evidence and status are updated.
