## 1. Verbatim approved matrix

| Status label                             | Exact meaning                                                                                                                           |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **GOOD TO GO**                           | Build and fully test locally now; no external account or credential is required.                                                        |
| **GOOD TO GO — LOCAL SUBSTITUTE**        | Build the complete Saha Textile behavior now using a console adapter, fixture or emulator; only external delivery remains untested.     |
| **BUILD FULLY; TEST AFTER TOOL ARRIVAL** | Implement production-grade code and automated provider-contract tests now; genuine provider E2E waits for credentials.                  |

| **PRODUCTION BLOCKED**                   | Local/test implementation may proceed, but production activation is prohibited until the stated dependency is satisfied.                |
| **DO NOT BUILD**                         | Explicitly outside the locked launch scope.                                                                                             |

## 2. Ratified implementation addendum

### 2.1 Route and contract ownership

| Boundary                  | Route family                                                                                      | Contract ownership                      | Implementation rule                                                                                                                                     |
| ------------------------- | ------------------------------------------------------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Shared browser security   | `/auth/csrf` and any deliberately shared session metadata endpoint                                | `packages/contracts` shared-auth module | Contains only behavior that is identical for storefront and admin; no audience-specific credential policy                                               |
| Storefront authentication | `/auth/storefront/**`                                                                             | Storefront-auth contracts               | Registration, password/email-OTP login, Google/Facebook verification, customer recovery, verification, customer sessions and customer continuation only |
| Admin authentication      | `/auth/admin/**`                                                                                  | Admin-auth contracts                    | Invite-only account creation, email-or-username/password, PIN, quick-resume, admin recovery, staff/admin sessions and security settings only            |
| Admin authorization       | `/admin/roles/**`, `/admin/permissions/**`, `/admin/users/**` or the existing approved equivalent | Admin RBAC contracts                    | Role, permission, assignment, offboarding and forced-session actions stay separate from authentication controllers                                      |
| Server internals          | No public route                                                                                   | Internal contracts and core ports       | Credential hashes, token fingerprints, provider payloads, Mongoose documents and framework types never cross the API boundary                           |

### 2.2 Language-agnostic API and reusable Angular consumption

- REST/JSON, standard HTTP semantics, cookies, ISO-8601 UTC timestamps, stable error codes, stable operation IDs, generated OpenAPI, and Zod boundary validation are the interoperability contract. No route may expose Angular, NestJS, Fastify, Mongoose, MSG91, Google, or Meta-specific types.
- Do not use JavaScript prototype mutation or monkey-patching as an API reuse mechanism.
- Each Angular app owns one typed auth gateway/facade boundary and one HTTP adapter. Components, routes, guards, SignalStores, effects, and feature code depend on that boundary rather than calling `HttpClient` directly.
- A shared transport primitive owns base URL resolution, `withCredentials`, CSRF acquisition/header injection, refresh single-flight, request correlation, safe error mapping, cancellation, and retry eligibility. It must not own storefront/admin business policy.
- Storefront and admin clients consume separate generated/typed route groups. Shared session/CSRF primitives are reused through composition, not through a god service or duplicated methods.
- API contract changes are made once in `packages/contracts`, reflected in OpenAPI, and adapted at the single HTTP-adapter entry point per audience. UI consumers must not manually propagate endpoint paths or DTO field mappings.

### 2.3 MongoDB scale and index rules

| Rule                       | Locked implementation expectation                                                                                                                                                                                                   |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Index from query shapes    | Every index must name the API/repository query it serves. Do not index every field. Use equality → sort → range ordering for compound indexes where applicable.                                                                     |
| Optional unique identities | Use normalized values and partial unique indexes for optional email, phone and username fields so `null`/missing values do not collide.                                                                                             |
| Auth lookup paths          | Unique indexes cover normalized identity and `provider + providerSubject`; token/code material is looked up only by cryptographic fingerprint/HMAC, never plaintext.                                                                |
| Session paths              | Index unique refresh fingerprint plus bounded user/audience/active/expiry access paths; rotation and reuse detection remain atomic.                                                                                                 |
| Expiring operational state | OTP, OAuth state, reset, verification and invite documents have explicit expiry indexes and application-level expiry checks because TTL deletion is asynchronous.                                                                   |
| RBAC paths                 | Role codes and active user-role assignment tuples are unique; permission-version changes invalidate stale authorization immediately.                                                                                                |
| Audit retrieval            | Compound indexes support actor+time, target+time, entity+time, action/outcome+time and retention-tier+time queries. Never TTL-delete legally retained security/financial evidence merely for convenience.                           |
| Pagination                 | Use stable cursor pagination with a deterministic tie-breaker such as `_id`; avoid deep `skip` pagination for growing orders, audit logs, users and sessions.                                                                       |
| Projections                | Read only required fields; never hydrate secret fields for public/admin projections. Prefer lean read models where domain mapping and invariants permit.                                                                            |
| Query bounds               | No unbounded list/export endpoint, leading-wildcard regex scan, client-defined sort field or unrestricted aggregation. Apply allowlisted filters, bounded limits, safe maximum time and asynchronous export seams.                  |
| Index lifecycle            | Disable uncontrolled production auto-index creation. Manage indexes through reviewed, idempotent migrations/ensure-index tooling and test the exact index catalogue with `listIndexes`.                                             |
| Explain-plan verification  | Seed realistic scale fixtures and assert critical query families use intended indexes rather than `COLLSCAN`; record execution statistics for regressions.                                                                          |
| Scale fixture floor        | Performance/plan tests include at least 1,000 products, 10,000 orders, representative customers/sessions, and multi-year audit history. This is a validation floor, not a production limit.                                         |
| Write-cost discipline      | Avoid redundant prefix indexes, unbounded multikey indexes, oversized compound keys and indexes on low-selectivity fields unless paired with a real query shape.                                                                    |
| Reporting/history          | Prefer bounded operational queries and materialized/reporting aggregates over repeated full-history dashboard aggregation. Archive only under an explicit retention decision.                                                       |
| Future scaling             | Do not add sharding, Redis, CQRS or another database without measured need. Keep repositories/ports swappable so replication, read scaling or a new adapter can be introduced without changing core use cases or Angular consumers. |

**Correction.** An earlier 2026-08-02 pass deleted all three screens on the reasoning that
a route with no endpoint behind it reads as supported when it is not. That reasoning holds
for the OTP screen only. `Admin password recovery request` and `Admin password reset` are
**GOOD TO GO** in §1 — instructions to build, not to remove — so deleting their UI exceeded

same milestone. Treat this row, not that pass, as the current disposition.

**What "repurposed" means for `/auth/otp`, concretely.** The route name is retained for URL
stability; the screen behind it is the recovery-token step. It accepts the single-use token
from the recovery email and passes it to `/auth/update-password` as a query parameter, so
the emailed link and a manually pasted token converge on one reset form. It is bounded so
the OTP-login reading cannot return:

- it does not inject the admin session store, so it can reach no login, OTP-verify or
  session method — enforced by the component's dependencies, not by convention;
- its field is a free-form token rather than a fixed-length numeric code, because the
  canonical credential is a long random token and a six-digit box invites a future
  challenge implementation;
- it performs no verification of its own and issues no session; the server consumes and
  validates the token on the reset request;
- the admin browser bundle contains no reference to any `email-otp` endpoint.

**Locked recovery behavior implemented alongside it.** A successful admin reset consumes the
token atomically, rejects a token whose audience is not `admin`, increments `tokenVersion`,
revokes every admin session, and moves the PIN into an explicit revalidation state that
blocks PIN full-login and quick-resume until the administrator authenticates once with the
new password. The PIN hash is retained rather than deleted, so the transition is auditable.
This state (`adminUsers.pinRevalidationRequiredAt`; formerly `users.pinRevalidationRequiredAt`
before `DEC-ACCOUNT-SEPARATION`) is deliberately distinct from the
five-failure `pinLockedUntil` brute-force lock, which expires on its own after fifteen
minutes; collapsing the two would let a timer silently restore a credential that a suspected
compromise had suspended.

**Known gap.** The API cannot yet tell a client _why_ a PIN was refused: the controller
raises a specific message, but the global error filter replaces every `401` with the generic
`unauthorized` envelope. A stable machine-readable sub-code is required before the admin UI
can distinguish "locked" from "suspended pending revalidation" from "wrong PIN"; until then
the login screen shows a standing hint that password login clears both conditions.
