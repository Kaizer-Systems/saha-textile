## 1. Why this task exists, stated accurately

The system today has **one `users` collection** holding both storefront customers and
back-office operators, discriminated by a `role` field of `customer | staff | admin`. That is
not an accident or a regression: it is the ratified design. It appears in the build prompt's
§8 target boundary list, in the security matrix's collection table, and as a single `users`
node in the ratified 64-node Schema Nebula graph.

The owner has since determined that this is wrong for this product, on two grounds:

1. **Access.** A storefront account and a back-office account should not be interchangeable in
   either direction. Today the block is one-directional — verified by probing a running
   instance on 2026-08-12:

    | Attempt                                            | Result                             |
    | -------------------------------------------------- | ---------------------------------- |
    | customer → `POST /auth/admin/login`                | **401** — blocked                  |
    | staff → `POST /auth/admin/login`                   | 200                                |
    | customer → `POST /auth/storefront/login/password`  | 200                                |
    | **staff → `POST /auth/storefront/login/password`** | **200 — ALLOWED**                  |
    | staff's storefront cookie → `GET /auth/admin/me`   | **401** — audience isolation holds |

    So a back-office operator can hold a storefront session. Session-level audience isolation
    does hold, which is what keeps that from being an immediate privilege escalation — but the
    accounts themselves are not separated.

2. **Shape.** A storefront customer accumulates saved addresses, contacts, sizes, measurement
   profiles, wishlists, consent history and more; an operator carries a username, employee
   code, department, inviter, PIN credential, lock counters and a preferred login method.
   Carrying both on one document means every read of either drags the other's fields, and
   every contract is a union of two unrelated things.

**This is therefore a change to a ratified architecture, not a bug fix.** It requires owner
sign-off on the decisions in §3 before implementation begins, and it amends canonical
documents that currently say otherwise.

## 1a. Naming — locked by the owner 2026-08-12

| Concept              | Physical collection | Contract entity | Id prefix (see D5) |
| -------------------- | ------------------- | --------------- | ------------------ |
| Storefront shopper   | `customers`         | `Customer`      | `cus_`             |
| Back-office operator | `adminUsers`        | `AdminUser`     | `adm_`             |

**`customers`, not `users`.** After the split, a collection called `users` holding only
shoppers is actively misleading, and "user" is the exact word whose ambiguity produced this
defect: it meant two populations at once, and nobody noticed because the name accommodated
both readings. Renaming removes the ambiguity rather than documenting it.

**`adminUsers`, not `operators`.** The codebase's own prose already calls these people
operators — the comments are full of it — and `operators` is arguably the better English. It
loses on consistency: `AdminUserProfile` already exists in contracts, `AdminUser` is already
the admin app's gateway type, the route family is already `/admin/users/**`, and the Schema
Nebula convention is camelCase nouns matching the domain object. Introducing a third word for
the same population would trade one ambiguity for another. Keep "operator" as the word used in
PROSE and comments; `adminUser` is the identifier.

**The rename reuses machinery that already exists.** `LEGACY_COLLECTION_NAMES` in
`collection-names.ts` maps an old physical name to its ratified one, and
`pnpm mongo:align-collections [-- --dry-run]` performs the migration: idempotent, refuses to
merge when both names hold data, never uses `dropTarget`, never runs at boot. Adding
`users: 'customers'` to that map makes the rename a reviewed one-line change on a path that is
already integration-tested. `test/collection-names.test.ts` additionally asserts that no legacy
key equals its target and that every target is a declared name — both hold for this pair.

**Do the rename and the split as SEPARATE sub-passes**, in that order (see passes 5a and 5b). The
rename moves one collection wholesale and is reversible; the split extracts rows by role and is
not. Combining them produces one migration that can fail halfway with no clean state to return
to.

**Cost to be honest about:** the Schema Nebula graph contains a `users` node and knows nothing
of `customers` or `adminUsers`. Both new names therefore need the temporary
`NON_GRAPH_COLLECTIONS` exception described in §2.1 — two, not one — taking the total number of
non-graph collections from three to five until the portal tool reconciles the graph. That is a
real, if temporary, weakening of a guard, and it must be recorded as owed work rather than
absorbed silently.

### A naming rule worth adopting at the same time

The bare noun **"user"** should stop being used for either population once this lands: it is
`customer` or `adminUser`, in identifiers, contracts, comments and prose alike. This is the same
shape of rule as the brand naming law (`scripts/check-naming.sh`, owner lock 2026-07-24), and
for the same reason — the failure was that one word quietly meant two things. Consider a
`scripts/check-account-naming.mjs` guard in `pnpm lint` once the split is complete, with
deliberate exceptions for the words that cannot change (`userId` on foreign keys until they are
renamed, `userAgentHash`, third-party APIs). Proposed as a follow-up, not part of this task.

## 4. Cross-cutting hazards — the things that will bite

### 4.1 Audit attribution becomes ambiguous

`auditLogs.actorUserId` and `targetUserId` are bare ids. With two populations, an id alone no
longer identifies a person. Every admin mutation writes one of these, and the audit read route
(`GET /admin/audit-logs`, added 2026-08-12) publishes them. Options: prefix the ids (D5), or
add an explicit actor/target population field. **Whichever is chosen, existing rows predate it**
— decide whether the read model tolerates rows without it.

### 4.2 Token and challenge collections

`passwordResetTokens` carries an `audience` and `completePasswordReset` already refuses a
mismatch. Verify the same for `emailVerificationTokens`, `otpChallenges` and `oauthStates`
before assuming; any that lack it can address the wrong population.

### 4.3 Rate limiting

`AUTH_RATE_LIMIT_POLICY` separates `storefront_login` from `admin_login` deliberately so
customer traffic cannot exhaust the back office's budget. Confirm the identifier scope is still
correct when the same address may exist in both populations (D1).

### 4.4 Session invalidation

`tokenVersion` and `permissionsVersion` are re-checked on every request by `SessionGuard`
against the user document. The guard must read the right collection for the session's audience,
or a revoked operator keeps working.

### 4.5 The last-administrator protection

Counts active ASSIGNMENTS, not accounts. It must keep working across the split, and the
first-administrator bootstrap must still refuse to run twice.

### 4.6 Deny-by-default guard

`scripts/check-route-authorization.mjs` (added 2026-08-12) enforces that role-gated routes
declare an audience and that role-only routes are justified in `ROLE_ONLY_ROUTES`. If route
keys change, that allowlist must be updated or the guard fails — which is the intended
behaviour, not an obstacle.

### 4.7 Formatting trap in the MDX documents

Prettier's MDX parser de-indents a list continuation line when an inline code span wraps across
a newline. Never let a code span straddle a line break in `project-progress.mdx` or the briefs.

- A customer account still cannot log in at `/auth/admin/login`.
- An operator's storefront session (if D8 permits a personal account) reaches no admin route.
- A customer id substituted into an admin route, and an operator id into a customer route,
  answer 404/401 — never a partial success.
- `/auth/admin/me` and `/auth/storefront/me` never return the other population's shape.

**Identity and collision**

- Per D1: the same email in both collections is either accepted everywhere or refused
  everywhere, with no path that silently creates a duplicate.
- Registration cannot create an operator; invite acceptance cannot create a customer.
- Anti-enumeration still holds on both surfaces after the split: known and unknown identifiers
  answer identically, including for an address that exists in the OTHER population — a new and
  easy leak.

**Credentials and sessions**

- Password reset, email verification and OTP each address exactly one population.
- `tokenVersion`/`permissionsVersion` invalidation works per population.
- Session list and per-session revoke stay scoped to the caller's own population and audience.
- PIN login, PIN lock and revalidation remain operator-only.

**RBAC and audit**

- Role assignment targets operators only; last-administrator protection survives.
- First-administrator bootstrap creates an operator and still refuses the second run.
- Audit rows attribute the correct actor across populations and the read model publishes no
  ambiguity.

**Migration**

- Splits a mixed collection correctly; re-running changes nothing; refuses when both are
  populated; `--dry-run` writes nothing.

**Ownership**

- A customer cannot read another customer's order or cart.
- The operator support-read path behaves exactly as D4 decides — and if it stays, it is
  exercised, because a bypass nobody tests is a bypass nobody notices breaking.
