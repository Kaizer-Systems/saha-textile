# Release Console

The Release Console is an owner-only dashboard for projects, their repositories, releases, servers and cloud accounts. It runs as one Docker container on the owner's Mac, and the same image can run on a server behind Cloudflare Access. It is in English only.

| Part          | Package                              | Where it runs                                                                     |
| ------------- | ------------------------------------ | --------------------------------------------------------------------------------- |
| Console app   | `apps/release-console`               | Angular, client-only; served by the console's own API process                     |
| Console API   | `apps/release-console-api`           | NestJS on Fastify, with its own SQLite database                                   |
| Mac helper    | `scripts/release-console/runner.mjs` | Node on the Mac, `127.0.0.1:4419`; reads the Mac and Docker, runs the local stack |
| Shared shapes | `packages/release-console-contracts` | zod schemas used by the app and the API                                           |
| Image         | `docker/release-console/`            | One image, one container (app + API + database), `127.0.0.1:4400`                 |

## Running it

```bash
pnpm console:up
```

From the main folder, this:

1. writes the console's key file from Infisical with the owner's own CLI login (`pnpm console:env`);
2. starts the Mac helper;
3. builds and starts the console container on `127.0.0.1:4400`;
4. waits until it answers.

`pnpm console:down` stops the container and the helper; the database volume is kept. `pnpm console:logs` follows the container's log. The helper refuses to start from a worktree, because it drives the stack and the pipeline in its own checkout. See `docker/release-console/README.md`.

While working on the console itself, `pnpm console` runs the app (Vite, 4400) and the API (4410) without Docker; the app then finds its API at its own port plus 10. The `release-console` and `release-console-api` entries in `.claude/launch.json` start them one at a time.

## The lock

The console opens behind a 6-digit PIN that is set on the first run, typed once and then again to confirm. A password can be added in Console settings; the lock screen then offers **PIN** and **Password**, opening with the one chosen there.

- The PIN is typed straight into the six boxes. The first box takes the keyboard when the screen opens; each digit moves to the next box, Backspace goes back, the arrow keys move between boxes, and a pasted or autofilled PIN spreads over the boxes. The sixth digit submits.
- The password has at least 12 characters. Setting, changing or removing it, and choosing which one the lock screen opens with, each need the PIN.
- Both are stored as salted scrypt hashes in the console's own database, never as typed and never in the Keychain.
- Five wrong tries of either lock the console for 15 minutes. The lock is kept in the database, so restarting the console does not lift it.
- Unlocking returns a random session token. The app keeps it in the tab's session storage and sends it as the `x-console-session` header. The API keeps sessions in memory only: they end after 30 idle minutes, on **Lock**, and when the console restarts.
- Every change that reaches beyond the console (starting a run, starting or stopping the stack, stopping a run) asks for the PIN or the password again. A wrong one counts toward the same lock, and a lock-out ends every session.
- Every route needs the session except `GET /api/health`, the `/api/lock/*` routes and the app's own files. A `401` sends the app back to the lock screen.

## Levels

The console has three levels. Search (⌘K) is on at every level and finds only what that level can open; it never looks across projects or into another repository.

| Level      | Address                       | Menus                                                                                                                                             |
| ---------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Console    | `/console/…`                  | All projects (grouped by workspace), Add a project, Attention, Audit (every project), Console settings                                            |
| Project    | `/p/:project/…`               | Overview, Repositories, Environments, Attention, Audit, Project settings (Connections, Repositories, Environments, Project menus, Remove project) |
| Repository | `/p/:project/r/:repo/:screen` | Overview, the repository's own menus, Ship, Watch, Run, one group per cloud platform, edge platform and secrets manager, Governance               |

The top bar holds the **Project** switcher (amber), the **Repository** switcher (cyan, with **Project overview** first) and the environment tabs of the open repository. The tabs show only on pages about one environment: Ship › Release (Live deploy, Release steps, What changed, Release impact, Approvals, Rollback), Run, Watch, Shop and Secrets. Pages about every environment, the whole repository or the whole account have none: the overviews, the console and project pages, Ship › Code, Ship › Plan and Packages, DigitalOcean, Cloudflare and Governance. Those pages label each resource with its environment instead. The console level has no environment tabs.

**Environment tags.** A droplet, managed database, Spaces bucket, Kubernetes cluster or App Platform app can be tagged with one of the repository's environments. The choices come from the repository, so an environment added later (Development, say) appears by itself. When a server create finishes, a box asks which environment the server is for, preset to the create's own environment; Cancel leaves it untagged. Later, the Environment column on DigitalOcean › Droplets › List opens the same box, and the Managed databases, Kubernetes, App Platform and Spaces screens have a **Tag environment** tab; each change needs the PIN. Tags live in the console's own file (`envTags`, per project and repository, for example `do:droplet:<id>` → `staging`). The API reads them with `GET /api/projects/:p/repos/:r/env-tags` and sets one with `PUT` (the key, an environment or `null`, and the PIN). Destroying a resource from the console removes its tag. A resource deleted on the vendor's own page loses its tag the next time the console reads its whole list.

**Environment labels.** Other rows on those pages get an **Environment** column worked out from what the console already knows (`packages/release-console-contracts/src/env-labels.ts`, shared by the API and the app):

- **Attached to servers:** volumes, snapshots, DigitalOcean backups, Cloud Firewalls, reserved IPs and load balancers follow the tags of the droplets they are attached to.
- **By domain:** Cloudflare DNS records (A, AAAA and CNAME only; mail and text records belong to no environment), tunnels, Access applications, Workers routes, edge and origin certificates, custom hostnames and the hosts inside rules. An exact domain wins, then a server's SSH host (`ssh-<environment>.<zone>`), then the longest domain the host sits under. A wildcard such as `*.sahatextile.com` covers every environment under it.
- **By branch:** pull requests by their target branch and runs by their branch. An environment with no branch of its own deploys from the repository's default branch.
- **Release calendar:** each freeze holds one environment or every one, and each day lists its releases by environment from GitHub's deployments.
- **Governance:** Audit labels an entry that names exactly one environment, Domains labels each edge certificate, and Costs adds **Servers by environment**, the monthly list price of each environment's droplets.

A row that matches several environments says `mixed:` and names them; one that matches none shows `—`.

Attention lists what needs the owner: keys that are expiring (14 days or less), expired or failed; vendor slots with no key; the latest run of a workflow on `main`, `staging` or `dev` that failed; and runs waiting for approval. The console level shows only project names and counts.

## Projects, repositories and vendor slots

A project has one or more repositories. Each repository has:

- **one source-code vendor**: GitHub, GitLab, Bitbucket or Azure Repos;
- **one or more cloud platforms**: DigitalOcean, AWS, Google Cloud or Azure; each environment runs on one of them or on this computer;
- **one or more edge platforms**: Cloudflare, AWS CloudFront with Route 53, or Fastly; each domain belongs to exactly one;
- **one or more secrets managers**: Infisical Cloud, Infisical (self-hosted), AWS Secrets Manager, Google Secret Manager, Azure Key Vault, Doppler, HashiCorp Vault or OpenBao, GitHub Actions secrets, or files on the server; each environment reads one of them, at a place inside it, or reads **no manager** (its apps use env files written by hand, outside the console, and the console reads nothing). An Infisical place is typed `project/environment` for the whole environment, such as `saha-textile-local/Development`, or `project/environment/folder` for one folder, such as `saha-textile-local/Development/api`. The environment can be its name as the Infisical dashboard shows it (Development, Staging, Production) or its short name (`dev`, `staging`, `prod`); the console saves the short name, because Infisical's command line takes only that, so the example is kept as `saha-textile-local/dev`. The older `project · environment · /folder` still reads. A self-hosted manager needs its server's address;
- **its own menus**, listed in its `.release-console.json`.

GitHub, DigitalOcean, Cloudflare and Infisical Cloud have screens; Infisical Cloud's is Run › Secrets, which its own menu group also opens. Any other vendor can be chosen; its group shows **Screens later** until its own screens are built the way that vendor works. Each vendor is an adapter behind one shape per slot (source code, cloud, edge) in `apps/release-console-api/src/vendors/`.

### Adding and changing repositories

**Add a project** walks through eight steps: name and workspace, repositories (a vendor each), environments and where each runs, cloud platforms, edge platforms with their domains, secrets managers and where each environment reads its secrets, the repositories' own menus, and a summary. **Next** stays off until the step is complete, with the reason beside it (owner, 20 Nov): a project name and workspace; at least one repository; a domain name for every environment (`localhost` on this computer) and a branch for every environment of every GitHub repository, once Connect has signed in; on Edge and DNS, an edge platform when any environment runs on a server, the domain each chosen edge holds, and every server domain under one of them; on Secrets managers, a choice for every environment (a manager ticked on the left with its place, or no manager), an Infisical place that reads, and a self-hosted manager's address. Cloud platforms follow the environments: a cloud an environment runs on is ticked by itself and cannot be unticked until that environment moves; any other cloud is ticked only by hand. Own menus are optional. **`.release-console.json`, version 2** (brief `26gq3NbcbBESea6abRtsa3`, approved 20 Nov): a repository describes itself to the console in one file at its root. `product` (name and kind), `parts` (each app, worker and data service with its compose service name, the domain it answers on, its health and operations addresses), `commands` (only `pnpm <script>` from the repository root), `deploy` (workflow files and the migrations folder), `secrets` (the name list), and the keys that turn on screens: `payments`, `messages`, `clients`, `seo`, `jobs`, `backups`, `links`, `menus`. Never a secret: keys stay in Infisical. Version 1 (`{"menus": [...]}`) still reads. The schema lives in `packages/release-console-contracts/src/release-manifest.ts`: an unknown key is reported as not used and a line it cannot read is skipped with the reason, so one bad line never hides the rest. The wizard's repository row says how many parts the file describes and which lines were not used. Governance › **Costs and quotas** shows DigitalOcean's month-to-date usage and balance (the DigitalOcean read key needs the billing read scope), read on opening and once a day. Governance › **Domains** lists each Cloudflare zone's edge certificates (the Cloudflare read key needs SSL and Certificates read) and checks every server environment's domain with a direct TLS handshake, read on opening and once a week, amber when a certificate has under 30 days left. Ship › Packages › **Dependencies** lists GitHub's open Dependabot and code-scanning alerts (both free for a public repository; the GitHub key needs those two read permissions), read on opening and hourly. Every one of these screens has **Check again**, shows when it was last read, and refreshes only while it is on screen. Run › Services opens with the **parts map**: each part from the file, joined to its container by its compose service name, with its state and health. The file is read again every minute and the containers every 5 seconds. Ship › Release › **Changes** compares each environment's branch with the next one's on GitHub (the commits a promotion would carry, with database migrations and secret-name changes called out), read on opening and every 5 minutes. **Search engines** (a repository's own menu, from `menus` in the file) runs our own checks. **Check the sitemap** has the Mac helper read the environment's `/sitemap.xml` (and every sitemap a sitemap index lists), then ask for each page it lists, one at a time and at most four a second, without following redirects. On this computer it checks the stack's shop with its own certificate, and on a server the environment's first domain. One check runs at a time and needs no PIN, because it only reads our own site. The result counts the answers (200, redirect, not found, other) and lists the pages that did not answer 200. The shop's "page not found" answers of the last 24 hours come from the edge's request log, which the console already reads every minute. They are kept per path for 7 days, with only the host a visitor came from (`google.com`, `this site`), never a query string. The edge logs that host alone (`referer_host`): it drops the scheme, sign-in, port, path and query before writing anything. nginx's error lines print the full request and referrer, so the Mac helper strips the query from their request and upstream parts and keeps only the referrer's host before any log line reaches the console. A path the sitemap lists that the shop cannot find shows red. The 404 list is read on opening and every 5 minutes. Google's own figures come from `GOOGLE_SEARCH_CONSOLE_KEY` (a service-account key for `release-console-search` in the Google Cloud project `saha-textile-production`, added as a Restricted user on the `sc-domain:sahatextile.com` property; the organisation blocks service-account keys, so the owner lifts that rule for that one project only while the key is made, then puts it back), kept once in `saha-textile-local` › `/release-console` because only the console reads it. Search Console sees the public site only, so these figures are the live website's whatever environment is open; the part of the screen that reads them comes next. A missing path the sitemap still lists offers **Open product** (or **Open page**) on the shop; any other offers **Add redirect**, which opens the admin's Redirects page with that path already filled in (`/redirect/create?source=`). **Client versions** lists which builds of the shop and the admin called in the last 24 hours, per app, with the installed app's share, read every minute. Each app is stamped with its build at build time (`BUILD_ID`: the first 12 characters of the code fingerprint, the same for the same code; the release record maps it to its commit) and sends it as `x-client-build` only on calls that change something (cart, sign-in, orders), which the browser already pre-checks for their CSRF header. Reads never gain a CORS pre-check, so the shop is exactly as fast; shoppers who only browse are not counted. A local `pnpm dev` build sends nothing. The edge logs the value as `client_build` and the console counts it with the request summaries. **Job queues** and **Messages** read the shop API's read-only operations address (`/ops/jobs`, `/ops/messages`): off unless `OPS_TOKEN` is set, at most 60 reads a minute, counts and statuses only. Messages never shows a destination, a message's text or a code. The console reads each environment with its own key, the same value as that environment's `OPS_TOKEN`: `CONSOLE_OPS_TOKEN_LOCAL` for this computer (saha-textile-local), `_DEV` for a development server, `_STAGING` and `_PRODUCTION`: this computer's stack through the Mac helper, a server on its `api…` domain. Both screens refresh every minute.

**DigitalOcean › Droplets › create** (Safe Releases Brief v7): the seven steps are tabs, in DigitalOcean's own order: Region (with the region's private networks), Image (OS versions, the Marketplace with a search, your custom images, snapshots and droplet backups), Size (shared or dedicated CPU, each CPU option and kind, every size with its price, dimmed where the region lacks it; **Build your own** drives DigitalOcean's v5 sizes with vCPU, memory and disk sliders), Storage and backups (a block storage volume, weekly or daily backups with their window), Sign-in (the account's SSH keys), Network and extras (IPv6, metrics and console agents, the first-boot file), and Name and confirm (how many, names, tags, project, what stops the create). Every list and price is read live from DigitalOcean when the steps open (`GET /api/projects/:p/repos/:r/cloud/:slot/catalog`, with the read key); a list the key may not read is named instead of hidden. The panel beside the steps shows the choices so far, the monthly and hourly cost and the exact `POST /v2/droplets` request; the first-boot file appears only as a mark, because its values are filled in on the Mac at create time and never reach the browser. Each environment starts from the agreed server (`<project>-<environment>`, blr1, Ubuntu 26.04, 2 vCPU · 4 GB for staging and development, 4 vCPU · 8 GB for production). **Reading states:** every screen shows the console's spinner in a banner while its first read runs, and the top bar says **Reading…** while any screen is still waiting for its first answer (refreshes do not count, so nothing flickers). **Create** (the last step's button) opens a box that needs the environment's name typed, the admin user's Recovery Console password twice and the console PIN; the API then runs one job, shown live on **Creating**: a Cloudflare tunnel named after the server (its token read for the first-boot file), the first-boot file filled in by the Mac helper (`scripts/release-console/first-boot.mjs`, the same filling as `pnpm server:create`: the admin's key is the first SSH key picked, the deploy key pair is made on the Mac and its private half stays in `~/.release-console/servers/<project>-<environment>/`, the password is hashed with `openssl passwd -6` and never kept), an optional volume, `POST /v2/droplets`, waiting for `active`, the addresses, the DigitalOcean project, a Cloud Firewall that lets in 443 from Cloudflare's ranges only, the environment's DNS records at Cloudflare (proxied; a record that already points elsewhere stops the job instead of being overwritten; production's records wait for the DNS switch) and, last, the tunnel connecting, which proves the first boot ran. A failed step stops the job and says why; every create and destroy goes to the audit log, never with a password or token. **Destroy a server** lists the project's staging and development droplets (production is never offered) and, after the typed name and the PIN, removes the DNS records that point at it, its Cloud Firewall, the droplet and its tunnel. Jobs live in the console API's memory, so a restart forgets an unfinished one (its resources stay and can be destroyed). Before the droplet, the same job gives the tunnel an SSH host name (`ssh-<environment>.<zone>` → `ssh://localhost:22`, its CNAME proxied), puts a Cloudflare Access application on it with two rules (the deploy job's new service token, and the people on the project's SSH list, changed any time under **Who may sign in over SSH** with the PIN), and sees to the certificates: the four `/infrastructure` files of the environment's Infisical place are reused when set; otherwise the console's machine makes the Origin Certificate's key and CSR (Cloudflare's Origin CA signs it for the environment's hosts, 15 years) and our own origin-pulls CA and client certificate (the client certificate goes to Cloudflare for those hosts), and saves the files to Infisical, from where every release installs them (`deploy.sh`). After DNS it turns Authenticated Origin Pulls on for the hosts, waits for the tunnel, sets the GitHub environment deploy.yml reads (made when missing; `SERVER_SSH_HOST`, `API_HOST`, `DEPLOY_SSH_KEY` from the Mac, `CF_ACCESS_CLIENT_ID` and `_SECRET`, secrets passed to `gh` on stdin) and reads the server's SSH host key through the tunnel into `SERVER_SSH_KNOWN_HOSTS` (this needs `cloudflared` on the console's machine: `brew install cloudflared`).

**Branches** (owner, 20 Nov): on Environments each environment picks the branch its deploys run from, in a search box with the branch icon that lists GitHub's branches plus the ones that exist only on the computer the console runs on (a branch never pushed). The refresh button beside it runs `git fetch` there and asks GitHub again; it never pulls. The first choice is suggested and shown for checking: the branch checked out on this computer for an environment that runs here, `staging` for Staging, the default branch for Production, `dev` for a development environment. Branches change afterwards only here or in Project settings › Repositories. A GitHub repository's `.release-console.json` is read only after Connect has signed in, from the branch of the first environment on this computer (the default branch until one is chosen), in this computer's checkout first and on GitHub otherwise. When the file is there, the row lists its menus and they arrive ticked on Project menus; when it is not, the row says so and the menus are ticked by hand on Project menus. Either way the project ends the same: the repository's menu starts with a group named after it holding those screens. A repository on another vendor gets its menus ticked by hand. The new project opens on its Connections tab.

Each step carries its own icon, and every provider shows its logo beside its name: on its card, on the buttons that pick where an environment runs or reads its secrets, in tables, beside domain and address boxes, and in the summary. Project settings › Repositories shows them the same way. The browser loads the logos from Iconify (`api.iconify.design`) when the screen opens; Infisical and Doppler, which Iconify lacks, show their own site icon through Google's favicon service. No logo is kept in the repository or on the computer, and without a network the provider's name shows on its own.

**Connect** (brief `QhMFJFyn5Gq1sosZ1AaTQG`, approved 20 Nov) links a GitHub repository row to the GitHub CLI (`gh`) on the machine the console runs on: the owner's Mac today, or the server the console is deployed to, on macOS, Linux or Windows. Every press opens a terminal popup (owner, 20 Nov: "let the terminal pop-up always be there"), which runs the helper's fixed script (`scripts/release-console/github-login.mjs`) and shows that machine's output step by step:

1. **Tools.** git, which `pnpm console:up` installs or brings up to 2.40 with the machine's package manager (`scripts/release-console/ensure-git.mjs`), then git's update check; then gh, the machine's own or a pinned release the console downloads into `~/.release-console/tools/`, checked against GitHub's published checksums, with no admin rights (`scripts/release-console/gh-tools.mjs`), then gh's update check. Each update check asks `[y/N]` in the terminal when there is an update (Homebrew updates what Homebrew installed, otherwise the console fetches the new gh; git goes through apt as root or winget, otherwise the check names the command to run) and says "No … update available" when there is none.
2. **Sign in.** A saved sign-in that still answers is named ("Already signed in to GitHub as …"). Otherwise gh's browser sign-in: a one-time code entered at `github.com/login/device`, from any device. **Paste a token instead** hands a token to `gh auth login --with-token` on standard input; nothing keeps it.
3. **Git uses this sign-in.** `gh auth setup-git`.
4. **Repository.** Whether the account can open it; a renamed repository is offered under its new name, and single sign-on is named when GitHub asks for it.

Once signed in, the page checks the repository and turns the row green, and the popup says so and asks "Close the terminal? [Y/n]".

Closing the popup before it finishes stops the sign-in and shows "GitHub connection cancelled." A signed-in account that cannot open the repository is said in the row, with **Use another account** and **Check again**, which open the terminal again. **Add project** links the sign-in as the GitHub key of every connected repository. The popup takes yes or no only for its own questions and runs no typed command.

The rest of the console follows the same rule. Every menu, screen, menu group, page title, tab, panel and search result has an icon; cloud, edge and secrets groups, the repository switcher, Connections and the project tables show the provider's logo; environment tabs show a laptop for this computer, a flask for staging and a globe for production; and this Mac's screens show the product each container runs (Node, Angular, NestJS, MongoDB, Redis, Meilisearch, Nginx or Docker). Icons are drawn in the colour of their text, so they dim, light and change colour with their item. The console fetches every icon once while the lock screen shows, so screens open with their icons in place. The icons live in `apps/release-console/src/app/shared/icons.ts`; a new screen needs an entry there, and a test fails until it has one.

Project settings › **Repositories** (also reached from a repository's **Repository settings**) changes a repository after the project exists:

- its role, environments (where each runs, its domains, and which secrets manager it reads and where), cloud platforms, edge platforms with their domains, secrets managers, and own menus;
- **+ Add repository**: a vendor and `owner/name`; the new repository starts with the first repository's environments, clouds and edges, keys included, and with the own menus of its `.release-console.json` when GitHub has one;
- **Remove repository**: the project keeps at least one repository, and its keys stay.

Slots that stay keep their keys. A cloud, edge platform or secrets manager added later starts without a key. Removing a cloud moves the environments that ran on it back to this computer; removing a secrets manager moves the environments that read it back to no manager. An environment can only run on a cloud, and read a secrets manager, that its repository has. Key ids the project does not hold are dropped when a repository is saved.

### Where the data lives

| What                                                                                         | Where                                                                                                                            |
| -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Projects, key links, PIN and password hashes, lock state, audit trail, stats and run history | `console.db` (SQLite) in the console's data folder: the Docker volume `saha_textile_release_console_data`, or `CONSOLE_DATA_DIR` |
| Key values                                                                                   | Infisical only (`saha-textile-local · dev · /release-console`), read by the console from its key file                            |

The database file is readable by its owner only. A console that ran before the database existed has its `console.json` and `audit.jsonl` imported once on first start; the old files are renamed `*.imported`.

The console starts with no projects. Every project, Saha Textile included, is added by the owner with **Add a project**, choosing its repositories, environments, cloud and edge platforms and own menus, and is then connected on its Connections tab. Nothing is imported on its own.

A repository's `.release-console.json` at its root lists only its own menus, for example `{ "menus": ["payments", "messages", "clients", "seo"] }`. The wizard and **+ Add repository** read it from the repository's default branch on GitHub and tick those menus. It holds no secrets and never adds a project.

## Connections and Infisical

Project settings › **Connections** lists every key by category and repository: source code, cloud platforms, edge, DNS and security, and secrets managers (with the environments that read each one). Below them:

- **Key file** shows the Infisical folder, when the key file was written, and the names it holds, lacks or leaves blank by choice. It shows names only, never values.
- **Keys** lists each key with its Infisical names, account, rights, expiry, last check and state, with **Check** and **Unlink**.
- **Link a key** offers each kind with where to make it and its Infisical name. **Use it for** lists the matching slots of this project's repositories, all ticked.

Keys never pass through the console. The owner saves each key in Infisical; `pnpm console:env` writes the console's key file from there with the owner's own CLI login, so no machine identity is used; the console reads the file again whenever it changes.

- When Infisical cannot be read, `pnpm console:env` keeps the last key file and says so.
- No answer from the API ever contains a key value, and the console's database holds only links.
- Unlinking a key or removing a project drops links only; the keys stay in Infisical.
- Every key is checked as soon as it is linked. The states are verified, expiring (14 days or less), expired, failed and unchecked.

| Infisical name                                           | Key                                 | Made where                                                                                                                                                                                       | Checked with                                                                                                       |
| -------------------------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `CONSOLE_GITHUB_TOKEN`                                   | GitHub fine-grained token           | GitHub › Settings › Developer settings: owner Kaizer-Systems, this repository only; Actions read and write, Contents, Pull requests, Deployments, Environments, Commit statuses and Secrets read | `/user`, repository access, and GitHub's own expiry header                                                         |
| none                                                     | GitHub CLI sign-in on this computer | `gh auth login`; works only when the console runs outside Docker                                                                                                                                 | `gh auth token`, then the same as above                                                                            |
| `CONSOLE_DO_READ_TOKEN`, `CONSOLE_DO_WRITE_TOKEN`        | DigitalOcean API · read / change    | DigitalOcean › API › Tokens, with an expiry; the change token is optional                                                                                                                        | `/v2/account`; DigitalOcean does not report a token's expiry, so the date typed when linking is used               |
| `CONSOLE_SPACES_ACCESS_KEY`, `CONSOLE_SPACES_SECRET_KEY` | DigitalOcean Spaces key             | DigitalOcean › Spaces Object Storage › Access Keys: Limited Access, the shop bucket, Read; linked with its bucket as `region/bucket` (for example `sgp1/saha-textile-media`)                     | Lists one object of the bucket, signed with AWS Signature Version 4                                                |
| `CONSOLE_CF_READ_TOKEN`, `CONSOLE_CF_WRITE_TOKEN`        | Cloudflare API · read / change      | The Cloudflare account that holds `sahatextile.com` › Manage account › Account API tokens; the read token uses **Read all resources**; the change token is optional                              | `/user/tokens/verify`; an account token is verified at `/accounts/{id}/tokens/verify`, which also gives its expiry |

The console never makes a token or signs in for the owner. A browser sign-in for other vendors (a GitHub App, DigitalOcean, GitLab, Bitbucket, AWS, Google Cloud, Azure) needs an OAuth application registered on that vendor by the owner. Cloudflare takes a pasted token only.

## Live screens

### Coverage

Ship › Code › Coverage shows how much of the code the tests run, for a CI run of any commit or for this Mac's latest `pnpm coverage`. Everything on it is worked out from Istanbul's coverage data, Vitest's test results and git, so it holds for any JavaScript or TypeScript code.

**Where the numbers come from.** `pnpm coverage` writes, for each workspace, Istanbul's line data (`coverage/<workspace>/coverage-final.json`), its summary, and each test's outcome (`tests.json`, written by `scripts/test-report/tests-reporter.mjs`, which keeps a failure's expected and received values apart and the lines it went through). It also writes `coverage/meta.json`: the repository root the reports' paths start with, the commit, branch and CI run, whether the copy had uncommitted changes, and each workspace's result; a run of some workspaces keeps the others' entries. The CI job **Tests at 100% coverage** keeps these files as the run's `coverage` artifact for 90 days, also when tests fail.

The console API reads a CI run through the repository's GitHub key (it needs Actions and Contents read): the run's artifact, unzipped with Node's own zlib, the commit's file list, and a file's text at that commit. This Mac's copy is read through the helper (`GET /coverage/meta`, `/coverage/report`, `/coverage/files`, `/coverage/text`, `/coverage/diff`). The helper refuses any file git ignores, so env files and keys never reach the screen, and it names its repository, so another project's screen does not show it. A run is read and added up once; the last three stay in memory.

**The tree.** Every file of the commit, folders first. Measured files show statements, branches, functions and lines; each folder shows the sums of the counts under it, never an average of percentages, up to the top row for the whole codebase. Shares are rounded down to one decimal, so 99.96% reads 99.9%. Green is 100%, amber from 80%, red below. A workspace whose tests failed carries a red pill. Filters: below 100%, measured only, lowest first; **Find a file** keeps the files whose names match; **Open every gap** opens every folder under 100%. **Changed in this commit** and **Changed since** the default branch keep only the files the change touched and say how many of its changed lines ran, against the rule that every change keeps its own code at 100%.

**A file at the side.** A click opens the file beside the tree, and the address keeps the file and line so a link opens the same view. **Lines** shows the code with syntax colours (highlight.js, for TypeScript, JavaScript, HTML, styles and JSON), how many times each line ran, a thin green edge for lines that ran, amber for lines that ran but not every way, red for lines that never ran, and each gap in words with the code quoted: `never true: <condition>`, `never false: …`, `never reached: the part before || was always true`, `never needed: the value before ?? was never empty`, `never called: name()`, `never used: this default value`, `never reached: this case`. A strip beside the code marks where the gaps are; a press jumps there. **Gaps** lists every gap in reading order, a block that never ran counted once. **Tests** lists the test files beside the file (`x.spec.ts` or `x.test.ts` there, or in its package's `test/` folder) with each test's outcome and time, and every failure in them or through the file: its message, expected and received side by side, and each line it went through as a link that opens that file at that line. A note warns when the file changed after its run, so its lines may have moved. The screen gives the facts that point to a failure's cause; it does not write the cause itself.

**Running a test file.** The Tests tab can run each test file beside the file, or holding a failure through it, on this Mac: the console PIN, then the helper's `test-file` job runs `vitest run` on that file in its own workspace (one test run at a time) and its log shows in the tab. The helper refuses anything that is not a `*.spec` or `*.test` file inside a workspace of `apps/` or `packages/` in this copy.

**Slowest tests and comparing runs.** **Slowest tests** lists the run's ten slowest test files. **Compare with** reads another CI run (or This Mac) and adds a Δ column: how each row's statements share moved since that run, ▲ up, ▼ down, ±0, or new.

**The map.** A folder's contents as boxes sized by their statements and coloured by how many ran, each folder box showing its own contents faintly. A folder box goes inside it; a file box opens the file.

**Keys.** `/` finds a file, Esc closes the file, `n` and `p` step through its gaps, `t` shows its tests, and the arrow keys, Enter and Space move through and open the tree.

## Releases, rotation and servers

### Changing passwords and keys

Run › Secrets › Rotate changes values for a server environment. Pick the values and why: **on a schedule** keeps the old sign-in, CSRF, mailbox and e-invoice and e-way bill keys for 30 days under `<NAME>_PREVIOUS`, so nobody is signed out; **after a leak** drops them at once. **Make new values** asks for the environment's name typed and the PIN, then the Mac helper runs `pnpm secrets:rotate -- <tier> --names <ids> [--no-grace] --json`, which makes the values and writes them into Infisical. The console keeps names and dates only.

| Value                                                             | What happens                                                                                                                          |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Database app, administrator and monitor passwords, Redis password | changed on the running service before the switch, no pause                                                                            |
| Search master key                                                 | search restarts, a few seconds                                                                                                        |
| Database keyfile                                                  | used from the database's next restart, or restarted now (about 20 s)                                                                  |

### Failed releases, rollback and the reachable card

When a run fails, Live deploy and Release steps read the failed job's log: a release step's name and message, the server's refusal, or its `FAILED:` line. After every finished run the console checks the environment through Cloudflare: `/health/live`, each host's record pointing at this server and proxied, the Full (strict) rule, origin pulls on each host, and the firewall's Cloudflare ranges. A broken check is named, with **Turn origin pulls on again** and **Roll back**, each with the PIN.

Ship › Rollback has two ways back. **Roll back** starts deploy.yml with `action=rollback`: the server swaps the previous release back in from images on its disk, passwords included. **Deploy an older version** runs the deploy on one release tag (`<environment>-<yyyymmdd-hhmmss>-<sha8>`, pushed after each healthy deploy); each GitHub environment accepts its own tags. After a leak, deploy forward instead: a rollback past a rotation brings the old values back.

### Creating a server

The create job runs these steps after the server is up:

- **Zone check**: Full (strict) by a configuration rule for the environment's own hosts only, Always Use HTTPS, and TLS 1.2 minimum. The rest of the zone keeps its SSL mode.
- **Staging login wall**: an Access application over the shop and admin hosts for the people on the project's SSH list; API hosts stay open for webhooks; production is not walled.
- **DigitalOcean DNS**: a host outside the repository's Cloudflare zones whose domain is delegated to DigitalOcean gets its record there, never overwriting one that points elsewhere; the firewall then opens 443 to everyone. The "Left for you" card then reminds you to set `EDGE_TLS=public`, `ACME_EMAIL` and the DigitalOcean DNS token in Infisical before the first deploy, so the server gets its own Let's Encrypt certificate.
- **Identity and approval**: `INFISICAL_IDENTITY_ID` from `docker/infisical/variable-names.json`, the GitHub environment's branch rule and its release-tag rule. A missing required reviewer is never set by the console; it stops the job.
- **Outside check**: ports 21, 22, 80, 27017, 6379 and 7700 on the public address must not answer.
- **Ready card**: what is left for you. Anything blocking fails the job with **Finish setup**, which gives the deploy token a new secret and redoes only the GitHub environment, the identity check and the host key.

Each server also gets a read-only **observer** login: an ed25519 key made beside the deploy key in `~/.release-console/servers/<project>-<environment>/`, forced on the server to `observe.sh`, and its own Access service token (`<server> observer`) kept beside the key with mode 600. The Mac helper sends only the requests `observe.sh` answers: `containers`, `logs <service>`, `releases`, `disk` and `db-report`.

The Creating tab lists each server's deploy token with its end date and **Renew token**; Attention warns 30 days before a token ends. DNS › The DNS switch moves the apex and www records to the production server after its checklist, with `production` typed and the PIN; Flip back restores the records from before.

## Checks

The shop's CI skips the console. A separate `console` job runs `pnpm check:console` (lint, types, tests and build) only when a pull request changes the console packages or shared setup files such as the lock file, root `package.json`, `turbo.json` or the CI file.

Live deploy follows where an environment runs (owner, 20 Nov), the same "this computer" and "server" split as the MSG91 rule. An environment on this computer runs `pnpm pipeline:local`. An environment on a server runs GitHub's `.github/workflows/deploy.yml`: it finds the commit's images in GHCR by its code fingerprint, runs CI, the production proof and the image publishing first when they are missing (never for production, which runs only images staging published), waits for the owner's approval on the GitHub environment, signs in to Infisical as that environment's deploy identity, writes and checks the release folder, opens SSH through the Cloudflare tunnel with an Access service token, and hands the folder to the server's deploy user, whose key can only run `docker/production/bin/receive-release.sh`. That script signs in to GHCR with the job's token, runs `bin/deploy.sh` (pull by digest, data services, release steps, switch, health) and signs out. The job ends with `/health/live` through Cloudflare, since the edge does not serve `/health/ready` from outside. The console starts the workflow with the PIN, reads the run's jobs and steps every 5 seconds while it runs, and approves the wait with the PIN. Servers are created with `pnpm server:create` (droplet, Cloud Firewall, `docker/production/first-boot.yaml`); `docker/production/README.md`, "A new server", lists the steps and the GitHub environment's names. A server environment whose name says development deploys to the `development` GitHub environment, which allows any branch: its Live deploy tab has the branch picker, and the picked branch is used for that one run, while its saved branch stays as set. Staging and production keep their branch locked, and the API refuses another branch for them. A development server also needs its own Infisical deploy identity and the release step's `development` tier.

**Deploying with blank values** (owner, 21 Nov; brief `26gq3NbcbBESea6abRtsa3`, screen 12). Opening a server's Live deploy tab reads its Infisical place at once, names only, and a banner counts the blank values a release needs (`docker/production/required-secrets.txt`) that would stop the deploy, with **Allow all** and **Check again**. Which of them a deploy may go ahead without is a positive list: the `may-deploy-blank` tag in that file, today `MSG91_AUTH_KEY` and the three Spaces keys, so a new required name can never be left blank by default. The Mac helper marks each `/api` row as required and tagged; the screen offers only blank, tagged names, and greys every other blank required value with its reason. The Spaces keys go together (the API refuses a media store with only some of them): they are offered only when all three are blank, and are picked and put back as one. Payment keys never stop a deploy, because the API starts without them and payments answer "not configured". Picked names show as chips inside the search box; ✕ puts a name back. Under the picker, **What runs** shows `deploy.yml`'s `allow_blank` input and the release step's `--allow-blank NAME` flags, and says what stays off (sign-in codes and texts for MSG91, photo uploads for Spaces). Production asks for `production` to be typed before Start. `deploy.yml` checks each name against the same tag before it signs in to Infisical; the release step checks again, writes the names it really left blank to `allowed-blank.txt` and `RELEASE_ALLOWED_BLANK`, `deploy.sh` skips exactly those, and the API skips only the MSG91 and media-storage checks for them (scripts/secrets and docker/production/README.md describe that side). The audit line lists the allowed names.

The console's browser tests run with `pnpm e2e:console` from the repository root. They start the console's API and app on ports 4412 and 4402 with an empty data folder, stats collection off and no Mac helper, and check the lock (a PIN typed into the boxes, a wrong PIN refused, Lock), the Add-a-project wizard, key states on Connections, Live deploy without the helper, and the alert rules, on a desktop and a phone screen.

## Reaching a server (SSH, SFTP, phone)

Port 22 is closed to the internet (plan §5); servers are reached through Cloudflare WARP or the browser terminal. Cloudflare Zero Trust must be switched on for the account once (team name, Free plan); until then creating a server stops before anything is made and says so. It is on since 22 Nov with the team name `saha-textile` (`saha-textile.cloudflareaccess.com`).

Zero Trust accounts made since June 2026 start with only "sign in with Cloudflare", limited to the account's members. The create job (and a change to the SSH list) adds sign-in by a one-time email code when it is missing, and sets WARP to include mode with each server's address, checking that the switch took: a new account starts in exclude mode, which sends all of a device's traffic through Cloudflare and leaves private addresses out.

- **WARP on any device**, signed in with an email on the project's SSH list (team name `saha-textile`, then the code sent to that email). The app is called **Cloudflare One Client** on Mac and Windows (formerly WARP, from Cloudflare's download page) and **Cloudflare One Agent** on iPhone and Android (App Store, Google Play). Device sign-in works once the first server exists: its create job writes who may sign a device in. the server's private address answers like any server's. iTerm and Windows `ssh saha-textile-admin@<private address>`, Mountain Duck or Cyberduck SFTP to the same address on port 22, Termius on iPhone or Android, `rsync`, `rclone` (SFTP remote) and `scp` all work with the admin's key. WARP carries only the servers' addresses (include mode), so nothing else on the device changes.
- **Browser terminal:** `https://ssh-<environment>.<zone>` in any browser, after a one-time code to the email.
- **Laptop without WARP:** `ssh -o ProxyCommand="cloudflared access ssh --hostname %h" saha-textile-admin@ssh-<environment>.<zone>` (or the same as a `Host` block in `~/.ssh/config`).
- **Break-glass:** DigitalOcean's Recovery Console with the admin's password from NordPass.

Each server's create job lists its own lines to copy. The first-boot file makes SSH listen on `127.0.0.1` and the private address only; the tunnel carries the private address as a `/32` route, removed when the server is destroyed.
